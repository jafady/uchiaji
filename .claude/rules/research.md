# 調査の進め方と書き方

## 進め方

- 調査は `researcher` エージェントにバックグラウンドで依頼する。互いに独立した調査は、並行して依頼する。
- 依頼には次を含める。
  - uchiaji のコンセプトの要点（`docs/concept.md`）と、ユーザーの関心（判断基準になる）
  - 調査対象
  - 知りたいこと
  - 報告の見出し
- 調査を待つ間も対話を止めない。結果が届いたら、research に反映したうえで要点を報告する。
- 結果を報告するときは、表で比べ、「uchiaji にとって何を意味するか」を添える。事実の羅列で終わらせない。

## 書き方

- `docs/research/` はカテゴリ別のファイルにする。調査を追加するときは、ファイルの末尾に足さずに、該当するカテゴリの該当箇所を更新する。当てはまるカテゴリがなければ、新しく作る。
- カテゴリの例：

  | ファイル | 内容 |
  |---|---|
  | `landscape.md` | 全体像、コンセプト比較、空白地帯 |
  | `<群>.md` | サービスのプロフィール。概要／特徴的な機能／活かす要素／反面教師 |
  | `case-studies.md` | 炎上・撤退・閉鎖の事例 |
  | `legal.md` | 規約・法律 |
  | `<技術テーマ>.md` | 実現手段の調査 |
  | `<UX テーマ>.md` | 体験設計のベストプラクティス |

- 1 つのサービスの情報はプロフィールに集める。サービスをまたぐ比較は `landscape.md` に置く。
- `docs/research/README.md` に、カテゴリの索引と更新履歴を置く。
- 事実の出所を区別する。

  | 表記 | 意味 |
  |---|---|
  | 【事実】 | 出典あり |
  | 【声】 | 利用者のレビュー・発言 |
  | 【推測】 | 筆者の解釈 |

  確認できなかったことは「未確認」と書く。
- 調査日を書く。価格や状況は変わる。
- 参考 URL は各ファイルの末尾にまとめる。

## 注意

- 法律に関する記述は一般論にとどめ、「法的な助言ではない」と明記する。
- 実在の人物の発言は、報道などの出典がある範囲で書く。
