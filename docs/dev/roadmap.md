# 開発の段階

uchiaji を、コンセプトから実装まで進める段階と、決めたこと。進め方の一般的な規約は [autonomous-development.md](autonomous-development.md) にある。

## 段階

2026-11-04 にユーザーと決めた。

| 段階 | やること | 人 | Claude | 状況 |
|---|---|---|---|---|
| 1. 公開リポジトリへ移す | 公開前の検査、リポジトリの作成、GitHub の設定 | コミット、作成 | 検査、設定 | 検査、コミット、リポジトリの作成、GitHub の設定（2026-11-04）は済み。main の CI 必須は 2b で足す |
| 2a. 要件を決める | MVP の範囲、未決事項、技術スタック | 対話 | 案と問い | 未着手 |
| 2b. 開発フレームを作る | エージェント、ルール、テンプレート、夕会のスキル | ― | 2a の裏で作る | 未着手 |
| 3. 画面のデザイン | 画面の流れ、デザインの方向、試作、デザインの決めごと | 対話。スマホで試作を触る | 案、試作、撮影 | 未着手 |
| 4. スパイク | iOS の PWA でのログイン、Workers からの取得 | 実機で確認 | 試作 | 未着手 |
| 5. 土台づくり（並行数 1） | インフラ、DB、共有の型、CI、認証、画面の部品 | 朝会・夕会 | 自動開発 | 未着手 |
| 6. 機能の実装（複数並行） | タスク割りのエージェントで並行開発 | 朝会・夕会 | 自動開発 | 未着手 |

- 2a と 2b は同時に進める。開発フレームは、プロダクトの中身にほとんど依存しないため。
- 技術スタックに依存する部分（コマンド、CI の中身）は、2a で決まってから埋める。

## 段階 1：GitHub の設定

| 対象 | 設定 |
|---|---|
| `main` | ルールセットで、PR 必須、CI 必須、force push と削除の禁止。迂回できる対象を置かない。CI 必須は、2b で最小の CI を作ってから足す |
| `develop` | 統合ブランチとして作る。ルールセットで、削除と force push を禁止する |
| マージ方法 | merge commit だけにする。squash にすると、develop と main の履歴が毎日ずれるため |
| マージ済みのブランチ | 自動で消す。develop のルールセットを入れてから有効にする |
| 秘密の混入 | secret scanning と push protection を有効にする |
| Actions | `permissions` を既定で読み取りのみにする |
| 外部からの書き込み | 外部の人の Issue やコメントを制限する |
| ラベル | `ready`、`in-progress`、`blocked`、`needs-discussion`、`contract-change` など |
| Environment | `production` に人の承認を必須にする |

## 段階 2a：土台づくりの前に決める要件

データの形に効くため、段階 5 より前に決める。

- 「原文」の定義（P-2 と P-6 の両立）
- MVP の範囲
- データの置き場所（端末内か、クラウド同期か）
- 技術スタック。調査での推奨は、Cloudflare（Workers、D1、R2、Access）のローカルファースト構成（[research/hosting.md](../research/hosting.md) の案 A。【推測】）

レシピの単位は、家族で 1 つ（うちの分量）に決めた（2026-11-04）。[concept.md](../concept.md) の未決事項を参照。

## 段階 2b：開発フレームの中身

- 規約とエージェントは、uchiaji 用に書き下ろす。ほかのプロジェクトの文面は写さない（2026-11-04 に決めた）。
- `.claude/` は git で管理する。クラウドのエージェントは、GitHub から取得したものしか読めないため。手元専用の `.claude/settings.local.json` は除く（`.gitignore` 済み）。

| 区分 | 対象 |
|---|---|
| レビュー | scope-reviewer、code-reviewer、security-reviewer、design-reviewer、ui-reviewer、dependency-auditor、license-auditor、doc-updater |
| 開発 | タスク割りのエージェント、開発エージェント |
| ルール | 変更の範囲、テスト、セキュリティ、アーキテクチャ |
| Issue テンプレート | 実装、不具合、ADR、調査、ドキュメント、リファクタリング、契約変更。「依存する Issue」「想定変更範囲」「対応する F-番号」の欄を持つ |
| PR テンプレート | 「人に見てほしい箇所」と「仮の判断」を中心にする |
| `.claude/settings.json` | commit と作業ブランチへの push を許可する。main への push と force push を禁止する |
| スキル | 夕会 |

- 開発、レビュー、タスク割りのエージェントは `model: opus` を明示する。
- クラウドの実行では、個人の `~/.claude/CLAUDE.md` が読み込まれない。日本語で報告すること、git の作法などは、リポジトリの `CLAUDE.md` に移す。

## 段階 3：画面のデザイン

| 順 | 成果物 | 内容 |
|---|---|---|
| 1 | 画面の流れ | 4 つの場面（出会う、決める、作る、振り返る）から、画面の一覧と遷移を図にする |
| 2 | デザインの方向 | スタンス（急かさない、決めつけない、ちゃんと覚えている）を、色、文字、余白、言葉づかい、動きに落とす |
| 3 | 試作 | 主な画面を、スマホで触れる HTML で作る。とくに「作る」と「振り返る」の画面 |
| 4 | デザインの決めごと | デザイントークンと部品の一覧を `docs/design/` に置く。並行開発で見た目がばらつかないための契約にする |

ui-reviewer は、スマホ幅での崩れ、台所での使いやすさ（文字の大きさ、片手での操作、押しやすさ）、アクセシビリティ、デザインの決めごととの一致を見る。

## 自動開発の費用

- アプリのランニングコスト（0 円の方針）とは別に、開発の費用として判断する。
- 段階 5（並行数 1）の間に、1 日あたりの利用枠の消費を測る。
- その実績を見て、段階 6 の前に、今のプランのままか上位のプランに上げるかを決める。
- 枠を超えたときの従量課金は、オフのままにする。
